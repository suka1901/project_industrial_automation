INA700 - EXAMINATION QUESTIONS AND ANSWERS
==========================================

Questions an examiner is likely to ask about this implementation, and the
answer in terms of what this system actually does. Where a number appears it
is the one in the code, so quoting it is safe.

The pattern that gets marks: say WHAT it does, then WHY that choice, then the
evidence. "The angle estimator reports the overlap as a confidence, because a
wrong angle with a good score is the one failure a gate cannot catch, and we
measured 184 labelled objects at five rotations each to set the threshold."


-------------------------------------------------------------------------
1. ARCHITECTURE
-------------------------------------------------------------------------

Q. Describe your architecture.
A. Ports and adapters, four layers, dependencies pointing one way only:

     domain          pure rules. Shapes, symmetry, angle arithmetic, the
                     pick area. No cv2, no numpy, no sockets.
     ports           nine abstract interfaces - what the application needs.
     application     the use cases: VisionPipeline, CoordinateService,
                     CycleController, the selectors, SharedState.
     adapters        everything touching the outside world: the Basler
                     camera, the NCNN model, ArUco, the TCP server, the GUI.
     infrastructure  Container (composition root), threads, config, logging.

   The application depends on the ports; the adapters implement them. No use
   case ever names a concrete class.

Q. Why bother? It is more files.
A. Three concrete payoffs:
   - The whole system runs with no hardware: swap the camera for a folder of
     photos and the robot for a loopback, and the same use cases run. That is
     how 321 tests run on a laptop in 15 seconds.
   - The Pi and the PC run different detectors (ncnn vs ultralytics) with no
     change above the adapter.
   - When the orientation estimator was replaced, nothing outside that one
     adapter changed.

Q. Show me SOLID in your code, concretely.
A. - Single responsibility: segmentation finds the object's pixels;
     shape_fit measures an angle from a mask; the estimator chooses between
     candidates. Three files, three reasons to change.
   - Open/closed: adding a segmentation route is one entry in
     CANDIDATE_MASKS - no existing code is edited.
   - Liskov: every FrameSource returns Optional[Frame] with the same
     contract, so CaptureWorker cannot tell a camera from a folder.
   - Interface segregation: nine small ports rather than one "Vision"
     interface. The colour classifier cannot accidentally grab frames.
   - Dependency inversion: CycleController depends on ObjectSelector and
     RobotTransport, not on CompositeSelector and TcpServerTransport.

Q. How do you know the layering is not quietly broken?
A. tests/test_architecture.py walks the imports and fails the build if
   domain or ports import cv2, numpy or any adapter. It is enforced, not
   promised.

Q. What is the composition root?
A. infrastructure/container.py, the only file that names concrete classes.
   main.py asks it for a frame source, a pipeline, a transport and so on.
   Changing camera.kind in the YAML changes the system without touching code.


-------------------------------------------------------------------------
2. MULTITHREADING
-------------------------------------------------------------------------

Q. How many threads, and what does each do?
A. Five workers plus the main thread:

     1 CaptureWorker     grabs frames from the camera
     2 InferenceWorker   runs the model: shape, orientation, colour
     3 MappingWorker     pixels -> millimetres, and the placing rotation
     4 CycleWorker       selects an object, commands the robot, verifies
     5 ConnectionWorker  accepts and watches the robot's connection
     main thread         the view (Tk needs the main thread)

Q. Why separate capture from inference?
A. They run at different speeds. The camera gives 15 frames a second;
   inference manages two or three. Coupling them would either throttle the
   camera or make the preview stutter. Separated, the preview refreshes at
   capture rate and the boxes at inference rate.

Q. How do the threads communicate? Any locks?
A. Bounded queues (sizes 2, 2, 2 and 8) plus one SharedState holding an
   immutable StateSnapshot behind an RLock. No thread touches another
   thread's data, so there is no lock ordering to get wrong.

Q. What happens when a queue is full?
A. put_newest DROPS the stale item and puts the new one. Deliberate: the
   robot must be told where the object is NOW. A queue that filled would
   hand it a position from several seconds ago - which would be a crash into
   the table, not a slow system.

Q. Does the GIL not make threading pointless in Python?
A. Not here, because almost nothing is pure Python. Grabbing a frame is I/O
   inside pypylon, inference is inside ncnn's C++ runtime, and OpenCV
   releases the GIL for the duration of each call. The Python code between
   those calls is a few microseconds. If the work were pure Python the right
   answer would be processes, not threads.

Q. How does it shut down cleanly?
A. One threading.Event shared by every worker. Each checks it between steps;
   ThreadSupervisor.stop_all sets it and joins with a timeout. The blocking
   stdin reader is a daemon thread, because there is no way to interrupt a
   pending read.

Q. Why is the GUI not a worker?
A. Tk insists on owning the main thread. That is also why typing commands is
   a command SOURCE on its own thread rather than a second view - it lets
   the window and the terminal both be live at once.


-------------------------------------------------------------------------
3. THE AI MODEL
-------------------------------------------------------------------------

Q. What model, and how was it trained?
A. YOLOv8n (nano, because the Pi has to run it), imgsz 640, 150 epochs with
   patience 25, batch 16. 216 training images and 55 validation images,
   labelled by hand; three classes - CIRCLE, SQUARE, STAR.

Q. Why only three classes when there are five shapes?
A. The task assigns three objects and says the model must NOT respond to the
   other two. Training on three classes is the strongest form of that: the
   model has no label to give a triangle or a hexagon. A selector rule
   (AllowedShapeSelector) enforces it a second time in software.

Q. Why NCNN on the Pi?
A. The same weights exported to a 12 MB runtime with no torch. Torch's
   aarch64 wheel fills the Pi's disk before it finishes installing. The PC
   runs best.pt through ultralytics; the Pi runs the ncnn export. Same
   model, two adapters, one ObjectDetector port.

Q. What is the inference time, and the requirement?
A. The requirement is under 3 seconds and the time must be printed every
   cycle - VisionPipeline prints it on every pass, and warns if it exceeds
   the configured budget. Measured on this Pi it is comfortably inside.
   (Quote the number you measured with ./run.sh bench on the day.)

Q. Confidence threshold?
A. detector.confidence 0.6. Raised from 0.5 because star precision was 0.886
   at 0.5 on the validation set - roughly one star report in nine was a
   hexagon or a triangle. Reporting a forbidden shape is worse than missing
   one, because the operator can simply ask again.

Q. What if the model misses an object?
A. The cycle reports "no object matched the request" and retries, up to
   three attempts in all. Nothing is sent to the robot on a guess.


-------------------------------------------------------------------------
4. COORDINATE TRANSLATION
-------------------------------------------------------------------------

Q. How do pixels become millimetres?
A. An ArUco marker (DICT_5X5_100, id 0, 100 mm outer black square) is
   printed at the centre of the A3 sheet, at (148.5, 210) mm. Its four
   corners are detected in the image, matched to their four known positions
   in millimetres, and a homography is solved from those correspondences.
   Every pixel then maps through that 3x3 matrix.

Q. Why a homography and not a scale factor?
A. A single pixels-per-millimetre number is only correct if the camera looks
   exactly straight down. A homography handles the perspective, so an object
   at the far corner of the sheet is as accurate as one in the middle.

Q. How often is it solved?
A. Every frame. If the camera is nudged, the next frame already carries the
   corrected mapping. That is also why pixels-per-millimetre is never stored
   anywhere in the config: a stored number is a number that can go stale
   without anyone noticing.

Q. What if the marker is hidden or blurred?
A. hold_last_good keeps the previous matrix rather than producing nonsense,
   and a scale_tolerance of 0.15 rejects a solve that disagrees with the
   marker's own perimeter by more than 15 per cent. Preflight checks marker
   detection and steadiness before a run.

Q. The marker gives you the SHEET frame. How does the robot know it?
A. wobj1 is taught on the sheet with the pointer, origin at the sheet corner
   with X along the 297 mm edge. The millimetres the Pi sends are in that
   work object, so the robot applies no transform at all - it moves to the
   coordinates as given.

Q. Why two work objects?
A. wobj1 is the picking sheet, wobj2 the jig the objects are placed in. Each
   is taught where it physically is, so moving either one does not disturb
   the other.


-------------------------------------------------------------------------
5. ORIENTATION - THE PART THEY WILL PROBE
-------------------------------------------------------------------------

Q. How do you measure an object's angle?
A. Segment the object inside its detection box, then sweep an ideal shape of
   the same kind through one symmetry period and keep the angle of greatest
   overlap. The overlap itself (intersection over union, 0 to 1) travels with
   the reading as its confidence.

Q. Why several segmentations?
A. No single one works on every object. otsu is brightness - good for a dark
   object on white paper. chroma is colour with brightness removed - it
   survives shadow and glare. gradient reads the STEP at the border - the
   only one that finds a white object on white paper. edges is Canny filled -
   strict but precise. The best fit wins, per object, per frame.

Q. Your angle is measured in the image. Is it not wrong by a constant?
A. It is, and it does not matter, because the placing rotation is a
   DIFFERENCE:

       rz = slot_angle - measured_angle

   The slot angles were measured with the same estimator through the same
   camera, so any constant offset appears in both terms and cancels. What
   must be right is that the reading TRACKS the object - measured at 0.03
   degrees median on stars and 0.77 on squares, over 184 labelled objects at
   five known rotations each.

   The corollary matters too: measure the slot angles with one estimator and
   run with another, and every placement is out by the difference. Preflight
   fails on exactly that, by reading measured_with from slot_angles.yaml.

Q. What is the symmetry period and why does it matter?
A. The smallest rotation that maps a shape onto itself: 90 degrees for a
   square, 72 for a five-pointed star, 0 for a circle. Every answer is only
   meaningful modulo that period, which is also a gift: the wrist never has
   to turn more than half a period, so a square is never asked for more than
   45 degrees.

Q. What is min_fit, and what happens below it?
A. 0.60. It is NOT a refusal - it chooses the route. At or above it the
   winning mask's own angle is used. Below it, the candidates' fit-weighted
   consensus is used instead and the log names the reading as a guess.
   Something is always sent: being a few degrees out is a worse placement,
   being unrotated is a wrong one.

Q. What was the hardest bug here?
A. A white square on white paper. Otsu has to choose which side of its
   threshold is the object and it chose the paper; the hole the object left
   was filled in, and the rectangle that remained fitted an ideal square at
   0.70 - above the threshold, so it was believed. The reported angle
   belonged to the CROP, which is axis-aligned however the object lies, so
   the error was the same every time and looked exactly like a mis-taught
   jig.

   Fixed by recognising the paper by its border: the crop is the detection
   box plus padding, so an object cannot reach the crop's edge. Measured over
   the labelled photos, every mask that found the object had a border
   fraction of 0.00 to 0.01 and every mask that found the paper 0.66 to 0.94.

Q. So a high confidence can be wrong?
A. That was precisely the lesson. A score computed from the wrong mask is
   confident nonsense, and no threshold can catch it. The fix had to be a
   test of whether the mask is an object at all, not a higher threshold.

Q. Is it lighting or software?
A. Both, and the split is measurable. A coloured square is measurable in any
   light we have shot in. A white one has 13 grey levels of separation from
   the paper at a dim sheet and 34 at a well-lit one, and the fit follows.
   ./run.sh light prints the sheet brightness and each object's contrast live,
   so the lamp can be aimed at a number. Light from the SIDE matters more
   than more light: a white face reflects what the paper reflects, but its
   edge still casts a shadow, and the gradient route reads the step.


-------------------------------------------------------------------------
6. COLOUR
-------------------------------------------------------------------------

Q. How is colour decided?
A. In HSV, over the object's own pixels - the mask, not the bounding box. A
   star fills barely a third of its box, so anything averaged over the box is
   mostly measuring paper. The colour whose hue range covers most of the
   object's pixels wins.

Q. White and black have no hue. How do you classify them?
A. By brightness relative to the paper the object is lying on, not by an
   absolute threshold - so the decision stays valid as the lighting changes.

Q. Where does colour enter the task?
A. Grade level II and III: pick only objects of a specified colour. It is a
   selector rule (ColourRequestSelector), so it composes with the shape rule
   and the pick-area rule rather than being special-cased.


-------------------------------------------------------------------------
7. COMMUNICATION
-------------------------------------------------------------------------

Q. Who is the server?
A. The Raspberry Pi. It listens on 0.0.0.0:5000; the robot is the client and
   connects to it. The address in ServerCommuncatio.sys on the pendant must
   therefore be the PI's address.

Q. What is on the wire?
A. Text, terminated by '#':

       move <shape> <x> <y> <rz>#      e.g.  move star 182.40 96.10 -31.6#
       quit#
       DONE:        / ERROR: ...       replies from the robot

   Colour is not sent. Matching the colour is the server's job; the robot
   only needs where, which shape's slot, and by how much to turn.

Q. Why the 80-character check?
A. A RAPID string is limited to 80 characters. The codec raises before
   sending, so the failure is one clear exception on the Pi rather than a
   silently truncated string on the robot.

Q. What if the robot never replies?
A. reply_timeout_s - the reply is awaited with a timeout, and a timeout is
   decoded as CycleOutcome.TIMEOUT, which costs an attempt rather than
   hanging the cell. The wait is long on purpose: a person has to press the
   yellow button.


-------------------------------------------------------------------------
8. THE ROBOT PROGRAM
-------------------------------------------------------------------------

Q. Walk me through the RAPID side.
A. PrepareCell sets the tool and work objects and moves to Phome. A command
   loop waits on the socket, parses "move shape x y rz", waits for the yellow
   button, then PickAndPlace: approach above the pick point, straight down,
   vacuum on, straight up, across to the slot, down, vacuum off, up, home.
   It replies DONE: or ERROR:.

Q. Why MoveJ for the transits and MoveL only near the object?
A. MoveL holds one arm configuration along the whole straight line and can
   refuse a reachable point for that reason. The path only matters where the
   cup meets the object - straight down onto it, straight up out of the slot.
   Everywhere else the fastest safe joint move is correct.

Q. What are ConfL\Off and ConfJ\Off doing?
A. Telling the controller not to insist on a stored arm configuration, and to
   choose one that reaches the target. Without them a perfectly reachable
   position is rejected for a configuration reason, which reads like a
   coordinate error and is not one.

Q. How is the rotation applied?
A. RelTool(placeTargets{shape}, 0, 0, 0 \Rz:=request.rotation) - a rotation
   about the place point's own tool Z, so the object turns in the slot
   without the point moving.

Q. Why the yellow button?
A. Safety, and it is a requirement of the cell: the Pi's command only puts
   the position in the robot's hands. Nothing moves until a person presses
   the button. The GUI says "PRESS THE YELLOW BUTTON" before the wait, not
   after, because the wait can be minutes and a status line claiming to be
   picking through all of it is how an operator decides the system has hung.

Q. What stops the robot picking off the sheet?
A. Two fences, and the robot's is the authority. StationData.mod has
   SHEET_MARGIN_MM = 15 and refuses anything beyond it with "off board". The
   Pi's own sheet.margin_mm is set to the same 15, so it never OFFERS an
   object the robot will refuse - a refusal would cost a whole attempt, and
   the retry would read the same scene and offer the same object again.
   A test reads both files and fails if they ever disagree.


-------------------------------------------------------------------------
9. ERROR HANDLING AND RELIABILITY
-------------------------------------------------------------------------

Q. What happens when a pick fails?
A. max_attempts is 3 - the first try plus the two retries the task allows.
   Between attempts the scene is read again, so a retry acts on what the
   camera sees now rather than on a stale position.

Q. How do you know the pick actually worked?
A. The robot says DONE:, and then the camera checks: the object must no
   longer be where it was, within verify_tolerance_mm (10 mm). The robot
   reporting success only means its program ran to the end - the cup can
   still have missed. The camera is the second opinion.

Q. What if a worker thread dies?
A. The supervisor's shutdown event is set and the window shows STOPPED
   rather than staying up looking healthy while every cycle silently fails.

Q. What are the limitations?
A. - A white object on white paper is marginal: that is contrast, and the
     honest fix is a side light, not a threshold.
   - Touching objects are segmented as one blob.
   - The marker must stay in view; if it is covered the mapping holds its
     last good solve rather than updating.


-------------------------------------------------------------------------
10. TESTING AND TOOLING
-------------------------------------------------------------------------

Q. How is this tested without a robot?
A. 321 tests, 15 seconds, no hardware. Mock detector, file-replay camera and
   loopback robot stand in at the ports. The domain layer needs no stand-ins
   at all - it is pure functions.

Q. Which test would you point at first?
A. test_architecture.py, because it checks the thing a reviewer cannot see
   by reading one file: that no dependency points the wrong way.

Q. What tools did you build for yourself?
A. preflight (is this Pi ready - camera, marker, lighting, slot angles),
   light (aim the lamp by numbers), bench (how fast the model runs here),
   check (the model against held-out photos), slot_angles (measure the jig),
   orientation_bench (score an estimator against known rotations). The last
   one is why the current estimator is the current estimator.

Q. How did you decide anything, rather than guess?
A. Every number in the config came from a measurement over the labelled
   photos, and the comment beside it says which. The orientation estimator
   was chosen by benchmarking two candidates over 184 objects at five known
   rotations; the confidence threshold came from the coverage-versus-accuracy
   table that bench prints.

11. IF YOU HAD MORE TIME
-------------------------------------------------------------------------

Good answers, because they show you know the weaknesses:

  - Split touching objects, by watershed on the mask.
  - Train on photos taken under the lab's own lighting, not only ours.
  - Close the loop on orientation: measure the object again after placing and
    correct the next placement.
  - Replace the yellow-button handshake with a proper safety interlock, so
    cycles can run continuously.
  - A non-white sheet would make the white object easy, and is the one change
    that costs nothing in software.
